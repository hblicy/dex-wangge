# Decibel 撤单确认修复设计

日期：2026-08-18

## 背景与根因

当前 Decibel 适配器在撤单交易被节点接受后，立即从 `_tracked` 删除订单；
`cancelAll()` 还会把一次 REST 快照里暂时缺失的本地订单视为撤单失败。Decibel
索引读取存在短暂延迟，机器人因此会在“链上已接受、索引尚未同步”的窗口里丢失
订单所有权，随后又通过对账重新接管或把订单判断为重复单，造成重复撤单。

新版 `WGALL-ZJ005-main` 的关键差异是：撤单请求成功只代表“已提交”，本地订单
仍保留；只有交易所连续快照确认订单已经消失后，机器人才能清除本地状态。

## 修复范围

本次只修复 Decibel 的撤单状态边界和 GridBot 对撤单结果的确认，不复制新版整个
Bot，也不修改 RISEx、PopDEX、网格价格、成交补单或下单参数。

具体调整：

1. `Decibel.cancelOrder()` 成功后不删除 `_tracked`。
2. `Decibel.cancelAll()` 只撤销当前交易所快照中可见的目标市场订单；单次快照
   没看到某个本地订单时，不据此返回失败，也不清除其本地跟踪。
3. 增加明确的 `forgetOrder(s)` 本地清理接口，只允许 GridBot 在远端消失得到
   确认后调用。
4. GridBot 的停止、重启、启动前清理和启动失败清理必须等待待决下单完成，再要求
   连续两次有效交易所快照证明目标订单已消失。
5. 空数组是有效快照；`null`、非数组、查询异常和结构损坏不是“零挂单”，必须
   保持本地状态并失败退出。
6. 对账过程中，撤单请求被接受后不立即删除活动订单；下一轮有效快照确认消失后
   才清理，从而避免索引延迟期间反复发起撤单。

## 状态与确认规则

撤单路径使用以下语义：

```text
ACTIVE
  -> CANCEL_REQUEST_ACCEPTED
  -> REMOTE_GONE_ONCE
  -> REMOTE_GONE_CONFIRMED
  -> FORGOTTEN
```

`CANCEL_REQUEST_ACCEPTED` 不是终态。确认期间如果订单再次出现在有效快照中，连续
消失计数归零；查询异常不得推进计数。确认在有界时间内未完成时，操作失败并保留
运行状态、订单跟踪和可追溯错误，不发送平仓指令。

对账触发的单笔重复单撤单同样保留本地跟踪。已提交撤单尚未确认时，不允许再次
提交同一订单的撤单；确认消失后再统一清理该订单的活动状态和撤单中状态。

## 可观测性

日志必须区分：

- 撤单请求已接受；
- 第一次远端消失；
- 连续快照确认消失；
- 撤单确认超时；
- 快照无效或查询失败；
- 因已有撤单正在确认而跳过重复请求。

日志只记录订单 ID、市场和状态，不记录密钥、签名或账户凭证。

## 测试与验收

测试先失败再实现，至少覆盖：

1. 单笔撤单成功后仍保留 Decibel 本地跟踪；
2. 批量撤单遇到暂时缺失的本地订单时，只撤可见订单并保留全部跟踪；
3. 一次空快照不能确认撤单，连续两次有效空快照才能清理；
4. 空、非数组、异常快照不能被当作撤单成功；
5. 待决下单未完成前不得开始最终撤单确认；
6. 撤单确认失败时停止、重启和启动失败清理均保留原状态且不得平仓；
7. 对账期间同一订单的撤单正在确认时不重复发送撤单交易；
8. 确认消失后本地订单、活动订单和撤单中标记全部清理；
9. Decibel 下单和成交补单现有行为不变；
10. RISEx、PopDEX 专项测试和项目完整测试继续通过。
