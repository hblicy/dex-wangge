# 网格成交补单持久化设计

日期：2026-08-16  
目标分支：`codex/risex-mainnet-adapter`

## 背景

RISEx 中性网格以 50 个初始挂单启动后，在成交和重连后稳定为 49 个。日志中的
`expected=49 REST open=49 WS buffered=49` 只证明本地、REST、WebSocket 对账一致，
不能证明网格成交后的替代单已经完整建立。

Decibel 与 RISEx 共用 `GridBot` 的“终态成交 -> 相邻层反向补单”逻辑。RISEx 写请求
需要签名并等待私有订单流确认，耗时明显更长，因此暴露了公共补单链路的异步时序问题：

1. 成交处理删除旧单后直接启动异步 `_place()`，没有等待补单完成便持久化状态。
2. `_place()` 成功后不主动持久化，新订单可能只存在于内存中。
3. 目标层已占用或正在下单时直接返回 `false`，没有区分“已被等价订单覆盖”和
   “本次补单意图尚未完成”，也没有可追踪日志。

## 方案比较

### 方案一：对账发现少于配置数量时直接补齐

实现简单，但无法知道缺失层应当是开仓单还是平仓单，可能重复开仓并造成单边仓位累积。
不采用。

### 方案二：在 RISEx 适配器内部复制 Decibel 补单策略

可以局部绕过时序问题，但会让交易所适配器承担网格策略，形成两套状态源，后续容易重复补单。
不采用。

### 方案三：修复公共成交补单事务（采用）

继续由 `GridBot` 作为唯一策略状态源。成交处理等待替代单得到明确结果，再持久化成交和新单的
一致快照；目标层已有等价订单时视为已覆盖，否则明确报警。RISEx 使用真实慢确认测试验证该行为，
Decibel 保持相同语义。

## 设计

### 成交处理

- 将每个成交事件加入串行成交队列，按收到顺序处理，避免多个相邻层同时成交时互相抢占目标层。
- 只有适配器发出的确定终态成交才能进入该队列，部分成交仍等待最终状态。
- 处理步骤为：删除终态订单、记账、计算替代单、等待 `_place()` 返回、最后调用 `_changed()`。
- 替代单下单成功后，持久化快照必须同时包含成交记录和新订单 ID。
- `suppressRequote`、回收阶梯和越界状态继续禁止补单，不改变现有安全语义。

### 网格层冲突

- `_place()` 返回结构化结果，至少区分 `placed`、`covered`、`blocked`、`failed`。
- 同一层已有方向、价格、数量和开/平仓语义一致的订单时，视为 `covered`，不重复下单。
- 同一层存在不等价订单时不得静默成功，也不得盲目叠单；输出包含层级、原订单和替代单摘要的错误。
- 进行中的同层下单必须等待其完成后重新判断，而不是直接丢弃补单意图。

### 失败处理

- 平仓/减仓替代单继续使用现有有界重试，失败必须报警并保留可见的待重试意图。
- 开仓替代单失败不自动无限重试，避免断线恢复后扩大风险；明确记录为未完成补单。
- 不根据“目标总数 50”盲目补单。数量恢复只能来自确定成交对应的替代单意图。
- 进程重启后的开放订单仍以 REST/WS 对账为准，不推测成交。

### 可观测性

每次终态成交记录：原订单 ID、层级、方向、成交数量、替代层、替代方向、结果和耗时。
层冲突和失败日志不得包含签名、permit 或私钥。

## 测试

1. 使用延迟下单的 fake exchange 复现：旧实现先持久化 49，补单完成后没有保存 50。
2. 连续相邻层成交必须按事件顺序补单，不得因 `_pendingLevels` 或旧订单尚未删除而丢失。
3. 等价订单已覆盖目标层时不重复挂单，计数不增长。
4. 不等价订单占用目标层时明确失败并记录日志。
5. `suppressRequote` 和批量撤单成交不得补单。
6. RISEx 适配器终态成交到 GridBot 的集成测试验证慢确认下最终快照包含替代单。
7. 完整 `npm test` 和构建检查通过。

## 完成标准

- 正常成交周期中，50 个初始网格在替代单确认后恢复为 50 个开放订单。
- 短暂下单期间界面可以显示 49，但不能在补单成功后长期停留 49。
- 对账一致但存在未完成替代意图时，健康状态或日志必须明确可见。
- 不引入按总数盲目补单、重复订单或新的单边开仓路径。
