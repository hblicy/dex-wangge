# PopDEX Stage 7 成交补单、恢复与 BTC 小网格验收设计

日期：2026-08-18  
分支基线：`codex/popdex-stage6-adapter-paper`  
目标分支：`codex/popdex-stage7-recovery`

## 1. 目标

Stage 7 在 Stage 6 的 PopDEX `IExchange` 实盘/Paper 适配器之上，实现：

- 可靠的成交识别和反向限价补单；
- 进程重启后的自有订单接管；
- 离线期间成交的恢复与一次性回放；
- 断线后的完整订单、成交和持仓对账；
- BTCUSDT 小额主网网格验收。

本阶段只完成 PopDEX 适配器与 GridBot 的内部集成，不接入正式服务器配置、API 和前端入口。Stage 8 才正式替换 Extended。Decibel 和 RISEx 的现有运行路径不得改变。

## 2. 明确不做

- 不开放 ETHUSDT 实盘网格；
- 不修改 Decibel、RISEx 的协议和恢复语义；
- 不依靠价格、方向或数量猜测订单归属；
- 不自动接管、撤销或平掉身份不明的订单/持仓；
- 不以实时流作为正确性的唯一来源；
- 不在本阶段删除 Extended。

## 3. 核心原则

1. 官方 REST 数据和本地持久化所有权共同构成事实来源。
2. 订单只能通过准确的 `orderId + clientOrderId` 关联。
3. 部分成交只累计，确认终态后才产生一次策略事件。
4. 所有写操作都必须在 `READY` 且对账数据未过期时执行。
5. 数据不完整或存在冲突时立即进入 `HALTED`，不得猜测或静默降级。
6. 断线恢复必须走与启动恢复相同的完整对账流程。

## 4. 架构与职责

### 4.1 PopDEX Order State

订单状态统一为：

```text
OPEN -> PARTIAL -> FILLED
  \-------> CANCELLED / REJECTED / EXPIRED
```

职责：

- 保存每笔自有订单的完整身份；
- 使用官方成交 ID 去重并累计成交数量；
- 保存订单终态和是否已完成策略处理；
- 仅生成一次终态策略事件。

### 4.2 PopDEX Ownership Store

每笔订单必须持久化：

- `marketId`
- `levelIndex`
- `side`
- `price`
- `sizeBase`
- `clientOrderId`
- `orderId`
- `opening`
- `reduceOnly`
- `parentFillEventId`（补单时）

所有权文件采用临时文件加原子重命名写入，权限为 `0600`。所有字段严格校验，解析失败不得返回空集合伪装成无订单。

### 4.3 PopDEX Reconciler

启动、定时轮询、手动重连和断线恢复共用同一个单飞对账器。对账器负责：

- 完整分页读取开放订单、订单历史和成交；
- 读取持仓与 Agent 授权；
- 将自有订单精确划分为活动、终态和冲突；
- 生成离线成交待回放队列；
- 对账完成后发布不可变快照。

### 4.4 GridBot

GridBot 保持策略所有者身份，仅新增可选的严格恢复能力：

- 保存适配器返回的完整订单元数据；
- PopDEX 恢复时使用适配器给出的精确活动订单，不按价格推算层级；
- 监听器和运行状态就绪后，串行处理待回放成交；
- 每次补单成功且快照落盘后，向适配器确认该成交已经处理。

其他交易所继续使用现有恢复路径。

## 5. 成交与补单语义

- 同一订单可有多笔成交，按官方成交 ID 去重。
- `PARTIAL` 不触发补单，原订单继续活动。
- `FILLED` 按最终累计成交量触发反向限价补单。
- 做多网格的反向卖单必须是 `Limit + GTC + ReduceOnly + OneWay/Net`，数量不得超过已验证的 BTCUSDT 多仓；不得用普通卖单代替 reduce-only，以免异常时反向开空。
- `CANCELLED/REJECTED/EXPIRED`：
  - 累计成交量为 0：不补单；
  - 累计成交量大于 0：按最终累计成交量补单。
- 撤单与成交竞态以官方订单终态和最终成交累计值为准。
- 批量撤单期间发现的成交仍计入成交统计，但设置 `suppressRequote=true`。
- 每个终态订单最多产生一个 `fillEventId`；进程重启不能重复统计或重复补单。
- 补单写入失败立即进入 `HALTED`，保留待处理事件和写操作日志。

## 6. 持久化与只处理一次

### 6.1 普通下单

1. 持久化下单意图；
2. 广播交易并保存交易哈希；
3. 根据回执和官方数据确认订单；
4. 将官方 `orderId`、`clientOrderId` 和网格元数据写入所有权记录；
5. 所有权记录原子落盘后，确认并清理本次未决写日志；
6. 返回 GridBot 并写入活动订单快照。

所有权记录是订单身份的持久化交接点；GridBot 快照滞后时必须从它修复，不能把已确认订单当成外部订单。进程在第 2 至第 6 步任意位置退出时，重启必须先恢复本次写操作或所有权事实，不能重新广播。

### 6.2 成交补单

1. 持久化终态成交和唯一 `fillEventId`；
2. GridBot 计算反向网格订单；
3. 使用由 `fillEventId` 派生的确定性补单意图；
4. 恢复时若官方已有该补单，则接管而不是重复下单；
5. 补单所有权和 GridBot 快照落盘后，将成交事件标记为已处理。

状态至少区分：

```text
DISCOVERED -> EVENT_PENDING -> REPLACEMENT_CONFIRMED -> COMPLETED
```

## 7. 重启与离线恢复流程

固定顺序：

1. 读取 GridBot 快照、所有权记录和写操作日志；
2. 校验账户、Agent 授权和 BTCUSDT 市场身份；
3. 完整分页读取开放订单、订单历史、成交和持仓；
4. 使用精确身份核对全部自有订单；
5. 接管仍活动的订单；
6. 将离线终态成交加入待回放队列；
7. GridBot 完成监听器绑定并进入运行状态；
8. 串行回放离线成交及补单；
9. 再次完整对账，成功后进入 `READY`。

离线期间多笔成交必须稳定排序后逐笔处理。任何一笔失败时停止后续写操作，保留剩余队列。

## 8. 断线和故障状态

- 读取失败或快照过期：进入 `RECONCILING`，暂停所有写操作。
- 网络恢复：重新执行完整对账，不能凭单次接口成功直接转为 `READY`。
- 下列任一情况进入 `HALTED`：
  - 本地订单在开放订单中消失，但订单历史和成交无法给出可靠终态；
  - 同一 `clientOrderId` 对应冲突订单；
  - 官方分页中断、游标循环或数据缺页；
  - 本地所有权记录与官方订单字段冲突；
  - 订单、成交和持仓无法闭合；
  - 补单写操作或持久化失败。

`HALTED` 后禁止自动补单、撤单和平仓，必须通过可靠对账或人工确认恢复。

## 9. 可观测性

日志必须包含：

- 对账原因、状态变化和总耗时；
- 每类接口的页数、游标和记录数量；
- 本地自有订单数、官方开放订单数、终态数、待回放数；
- 脱敏后的 `orderId/clientOrderId/fillEventId/levelIndex` 关联；
- 补单意图、官方确认结果和恢复路径；
- 进入 `HALTED` 的首个根因。

后续重复错误不得覆盖最初根因，周期性相同日志需要节流，但状态变化必须完整记录。

## 10. 自动化测试

### 10.1 状态机

- 多次部分成交；
- 重复成交 ID；
- 撤单与成交竞态；
- 零成交取消；
- 部分成交后取消；
- 终态事件只生成一次；
- 批量撤单期间成交不补单。

### 10.2 故障注入

在下单广播前、广播后、回执后、官方确认后、所有权落盘前后、Bot 快照前后模拟崩溃，验证：

- 不漏掉已接受订单；
- 不重复广播；
- 不重复补单；
- 不接管外部订单。

### 10.3 恢复与断线

- 正常重启接管；
- 离线期间一笔或多笔成交；
- 分页中途失败或游标循环；
- 接口恢复但数据尚未闭合；
- 本地/官方身份冲突；
- 完整对账后才恢复 `READY`。

### 10.4 回归

- 完整 Node 测试；
- Grid 测试；
- Decibel、RISEx 关键补单和恢复测试；
- PopDEX Paper 测试。

## 11. BTCUSDT 主网小网格验收

参数：

- BTCUSDT；
- 做多 3 格；
- 1x 杠杆；
- 每单约 10–15 USDT，且必须满足官方最小名义价值；
- 人工选择较窄区间，确保至少触发一笔成交和反向补单。

Stage 6 只验证并开放了 BTC 多仓平仓，尚未验证空仓平仓。因此 Stage 7 不允许用中性或做空模式进行主网验收，避免先成交卖单后形成无法由适配器安全平掉的空仓。

Stage 6 尚未开放 reduce-only 限价写入，而做多网格成交后的卖出补单必须使用该语义。Stage 7 需要先根据已记录的官方订单参数实现严格编码、模拟和回读校验；若模拟、回执或官方订单任一处不能确认 `Limit + GTC + ReduceOnly + OneWay/Net`，立即 `HALTED`，不得退化成普通卖单。

本阶段提供独立的 `popdex:grid-probe` 验收命令，不注册正式服务器路由，也不修改前端。命令默认只读预检；只有显式提供主网确认参数才允许启动 3 格做多网格。命令至少支持：

- `start`：严格预检后启动；
- `status`：只读显示订单、成交、持仓、恢复队列和健康状态；
- `resume`：按持久化事实恢复，不执行未经确认的新写入；
- `reconnect`：触发完整只读对账；
- `stop`：撤销自有订单并使用已验证的多仓路径确认归零。

验收命令使用独立状态文件，避免读写正式服务的 `.state.json`。同一主账户、同一市场存在外部订单或持仓时拒绝启动。

验收步骤：

1. 确认初始挂单和持仓均为 0；
2. 启动小网格并核对初始订单身份和数量；
3. 至少成交一笔，确认只挂出一笔方向、层级、价格和数量正确的反向限价单；
4. 正常重启，确认接管且不重复挂单；
5. 人工制造读取断线，确认暂停写入并进入 `RECONCILING`；
6. 恢复网络，确认完整对账后进入 `READY`；
7. 在离线窗口产生一笔成交，恢复后确认只补一次；
8. 停止网格，确认挂单 0、持仓 0；
9. 保存程序日志和官方订单/成交记录作为证据。

BTC 验收全部通过前，不开放 ETHUSDT 实盘，不进入 Stage 8 正式替换 Extended。

## 12. 完成标准

- Stage 7 自动化测试全部通过；
- Decibel、RISEx 回归测试通过；
- 所有恢复场景均按精确身份处理；
- 失败场景能够稳定进入 `RECONCILING` 或 `HALTED`，没有静默兜底；
