# PopDEX Stage 7 停止可观测性设计

## 背景

`popdex:grid-probe` 的 `stop` 会依次等待撤单、订单终态确认、最终订单/仓位对账和恢复文件清理。当前交互式 CLI 在整个过程中没有阶段输出，成功结束时也没有明确提示。主网实测中，交易所已经撤单、账户已经空仓且恢复文件最终被正确清理，但操作员无法区分“仍在安全确认”与“程序卡死”。

本次只改善 Stage 7 独立验收 CLI 的可观测性和控制命令串行化，不改变 PopDEX 下单、撤单、平仓、对账、恢复或文件清理判定，也不改服务器、API、前端、Decibel 或 RISEx。

## 行为设计

交互式和测试注入的 `output` 使用同一日志路径。收到 `stop` 后按顺序输出：

1. `正在停止：撤销挂单并确认终态`，包含开始时的挂单数和是否有持仓。
2. `撤单阶段完成`，表示 `GridBot.stop()` 已完成撤单及必要的平仓确认。
3. `正在执行最终订单/仓位对账`。
4. `最终对账完成`，包含剩余活动订单数、pending 成交事件数和是否有持仓。
5. 清理恢复文件和锁文件成功后输出 `PopDEX 三格验收已安全停止`，包含总耗时。

日志不输出私钥、完整账户地址、交易签名或未经脱敏的错误内容。订单数量、pending 数量、持仓布尔值和耗时可以输出。

## 错误与恢复

每个停止阶段由 CLI 记录当前阶段。任一阶段抛错时，输出 `PopDEX 停止失败`、阶段名称和耗时，然后继续抛出原错误；不吞错、不改写错误原因，也不清理恢复事实。

只有最终对账严格满足 `READY`、活动订单为零、pending 成交事件为零、BTCUSDT 空仓，且恢复文件清理完成后，才输出成功提示。

## 控制命令串行化

会话增加一个内存中的控制命令锁。`status`、`reconnect` 或 `stop` 执行期间收到另一条命令时立即报错，提示当前命令仍在执行；不排队、不并发，也不重复发送交易所写操作。

锁只覆盖单次进程内的交互命令。进程崩溃后的恢复仍完全依赖既有 operation journal、ownership 和 probe snapshot。

## 测试

自动测试至少覆盖：

- 成功停止时阶段日志顺序固定，并包含最终成功和耗时。
- 最终对账失败时输出准确失败阶段，不打印成功，不清理恢复文件。
- `stop` 尚未完成时再次执行任意控制命令会被拒绝，且不会重复撤单。
- 交互式 `runGridProbe` 在成功停止后打印最终结果并退出。
- 全量测试继续覆盖 Decibel、RISEx、PopDEX 及安全边界，无回归后才允许发布。

## 验收标准

- 操作员输入 `stop` 后立即看到阶段进度。
- 正常停止最终明确显示安全停止、挂单零、pending 零、持仓零和耗时。
- 失败能从日志确定具体阶段，恢复事实保持可用。
- 重复控制命令不会造成并发读写或重复广播。
- 交易逻辑及安全判定与当前 `main` 完全一致。
